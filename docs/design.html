Design and requirements, draft for review

Tycho Station

A local code factory. A root session takes a body of work, splits it into work units, and hands each one to a control session that plans, delegates, verifies and escalates but never edits code. Every process lives under zmx; the terminal app, the inbox and the web view are disposable readers. Blockers climb a ladder of arbiters with case law at each rung. The human sees a decision packet, not a transcript.

1Purpose and success test

One or more root sessions act as the entry point for a body of work: an epic, or something open ended. A root is an orchestrator of orchestrators. For each work unit it spawns a child control session, a separate CLI agent process in its own worktree. Control sessions spawn workers with an explicit model and effort. Subagents inside one session and agent-team modes are not sufficient: they cannot be nested, cannot be resumed independently, and die with their parent.

The factory is done when the following holds on a synthetic epic.

Five work units run end to end with at most one human interrupt. That interrupt is a decision packet a cold reader resolves in under five minutes. A kill of Ghostty, the reader, or the core mid-run loses nothing.

3Decisions taken

Scope

Repo and host agnostic. Nothing assumes a monorepo, a language, a layout or a git host. The factory's own state never lives inside a target repo, and the merge gate is local git.

Vendors

Control sessions and workers may be Claude, Codex, Antigravity, Amp or OpenCode. The protocol is vendor neutral. Anthropic usage runs on seat-based subscription auth.

Autonomy

No human in the merge loop. A child declares a unit done and the core merges it mechanically once verification passes. The ceiling is ownership: children cannot write to the canonical repo at all. Prose instructions are not a gate.

Prior art

Reference only. Borrow shapes from Symphony's state machine, Gas Town's escalation record and Omnigent's Polly rules. Adopt no framework.

Human surface

Ghostty shows sessions, zmx holds them, and one Rust reader provides the inbox, TUI and web view and lands a human in the right Ghostty tab. No dedicated terminal app is on the critical path.

Process ownership

zmx owns every long-lived process. The terminal app, the TUI and the web view may crash at any time without losing a session.

Durable execution

Restate runs the orchestration: one binary with an embedded journal, Rust SDK, keyed objects and workflows. Agent runs are side effects outside the engine; the engine owns retries, timers, signals and replay.

Trust boundaries

Agents, the factory core and the human are three trust domains. Agents run under their own user with no credentials at all; the core's handlers that change authority are not callable from ingress; the canonical repo and its default branch are writable only by the core.

4Topology

5Process supervision

zmx creates the same kind of session whether run or attached: a daemon per session, tied to the lifetime of the PTY process, not to any client. Every level is created the same way and fan-in is native.

zmx run cf7a.wu03.ctl.codex -d exec /usr/bin/env -i HOME=... PATH=... TYCHO_CORE_UID=<uid> tycho launch --spec <spec file> --tier <tier>
zmx run cf7a.wu03.wrk.claude.a1f3 -d exec /usr/bin/env -i HOME=... PATH=... TYCHO_CORE_UID=<uid> tycho launch --spec <spec file> --tier <tier>
zmx wait cf7a.wu03.wrk.*          # fan-in on every worker of work unit 03
zmx history cf7a.wu03.wrk.claude.a1f3 --html   # scrollback as evidence, no attach

Three properties shape the design. Kill is SIGHUP then SIGKILL half a second later, so there is no shutdown window and workers checkpoint continuously. zmx restores scrollback, never agent state, so every restart reads a manifest the factory wrote. Nothing bounds the session count and a finished run does not end its session, so reaping is the factory's job.

The factory pins the latest zmx release (0.8.1 at the time of writing, probed directly) and creates every session itself. Facts from the probe that shape the launcher: send reaches the stdin of a program started with a detached run, so nudges need no attach and steal no focus; killing a daemon ends its shell and any job with default hangup handling, but a job that traps hangup survives as an orphan the session list no longer shows, which is why kill goes by the recorded pid and not by session name alone while the session's program runs; once zmx lists the session as ended its pid may belong to another process, so the entry is removed by name and the pid is never signalled; the socket path has a length limit, so the socket directory is short; labels are set after a detached run, not with it; 0.8.1 does not accept a -- after -d, which it types into the shell as a command that exits 127, so sessions are spawned without it; prefixing the typed command with exec makes the listed pid the program's own and ends the session with the program, while without it the entry stays listed as ended. Agent sessions live in a socket directory shared with the developer's group so Ghostty can attach from the developer's account; the core's own sessions live in a separate directory, because zmx does not check who connects and any group member can send to or kill a session. Internal spawns always use run with a detached flag, never a bare attach, because a session's own identity is inherited by its children and an attach would hijack the calling terminal. One human viewer at a time: whichever attached client types becomes the leader and resizes the pty, so the reader tails output rather than attaching.

Two sessions are factory-wide rather than per epic: the Restate server and the Rust service endpoint. A launchd watchdog outside zmx starts both at login, probes their liveness, and restarts whichever is missing; it is the one supervisor that cannot be inside the thing it supervises. After that, Restate's own retry and replay do the rest. If the server dies, its journal is on disk and every invocation resumes on restart. If the service endpoint dies, Restate retries the in-flight handlers against it once it is back. Agent sessions sit outside both and keep running under zmx; the awaitable each one was handed stays pending until its launcher resolves it. The reconciler is its own keyed object, not a handler on the epic: it re-sends itself with a delay, compares expected sessions against lease files, and marks dead ones so the owning workflow re-queues them.

The production core listens on fixed loopback ports: Restate admin 19070, ingress 18080 and node 15122, and the endpoint 19080; the test suites' in-process endpoint takes 19081. A test core moves all five by a port offset its suite claims for the test home: the first eight bytes of the SHA-256 of the home's path pick a starting slot among 1800, the suite takes an exclusive lock on ~/.tycho-port-slots/<slot> for the core's life and moves to the next slot while one is held, and the offset is 1024 plus 16 per slot, at most 29808 (PORT_OFFSET_MAX), which keeps the highest port below the macOS ephemeral range at 49152. No two production ports differ by a multiple of 16, so cores at different offsets never share a port; a unit test checks every slot. The suite sets the offset as TYCHO_PORT_OFFSET beside TYCHO_HOME, and the core refuses the variable for the default core home, so the production core keeps its ports. The core's configuration forwards the offset to the endpoint's session, the watchdog's plist and every launch spec, and the health probes, the endpoint registration, the operator commands and the launchers' ingress calls all read the ports from it. The claim also binds all five ports and passes over a slot whose ports a process outside the test cores holds, naming it in the test's evidence; a port collision fails a test only when no slot is left. The spine, kill, launcher and chaos suites run at the same time, across worktrees as well; the worker and control suites run one at a time, because they share the developer's vendor seat, which their mise task descriptions state. After slice one the offsets are reviewed against review turnaround: if running suites concurrently did not shorten it, the offsets are removed in favour of a lock file that runs one suite at a time.

A session is alive when its lease is fresh, not when it appears in the zmx list. The launcher writes a lease file with its pid and a heartbeat timestamp, and its exit trap kills its own zmx session, so finished sessions do not linger. A spawn step whose session name already has a fresh lease adopts it; a stale lease means re-queue. This matters because zmx run on an existing name types the command into that session's shell rather than failing, so the lease is what makes a replayed spawn safe. The lease carries a digest of the awaitable id, never the id itself, and an ended marker written once the result is acknowledged, so a replayed spawn adopts a finished session as ended rather than judging it stale. A tick that fires after a host sleep longer than the freshness window, before the launcher's next heartbeat, reads the lease as stale and expires and reaps the session without re-checking it; a known gap.

Headless worker results

The launcher runs tycho worker as a headless worker's vendor process. It checks the vendor's version banner against the pin, runs the headless command in the worktree with the brief on stdin, folds the event stream into the progress file, and writes the result file the launcher's exit table reads. A completed result claims done when the worktree's HEAD moved from the base commit and not done otherwise. Words that no exit state names decode as unrecognised and block in the inbox instead of re-queueing.

The launcher runs every vendor through tycho session-leader, which makes it the leader of a new session with no controlling terminal: under zmx the session's pty is the launcher's terminal, and a vendor in a background group there would be stopped by any tool that sets terminal modes, such as stty in a login shell's startup file. The new session's group id is the vendor's pid, so the launcher's group signal reaches the vendor and everything it starts. Between setsid and exec the trampoline applies the session sandbox (the session sandbox, section 7), and the worker runs in its worktree, inside it: a vendor started from a directory the sandbox does not grant cannot read its working directory, and the pinned Claude CLI then fails even --version. Before a unit attempt's first headless task, the WorkUnit run clones the attempt's worktree from the canonical repository on the branch <unit>/a<attempt> and builds its graph index; at each result it fetches the branch into the canonical repository, writes the pin ref, records the checkpoint and, when the worker committed, rebuilds the index. Each build's time is recorded in the unit's view, and a failed build is recorded without stopping the worker. A worker that cannot finish writes a certified question to the file TYCHO_ESCALATION_FILE names, in an escalation directory beside the result and progress files, in the session's vendor directory under the spool, the one directory of the session the sandbox lets the vendor write; the adapter adds the escalation directory to the session's directories; whatever the stream says, the result is then escalated with an escalation envelope, and the launcher rejects the awaitable with escalated, a newline and the question. A question that does not decode is vendor_escalation_invalid (inbox).

Claude, pinned at 2.1.280, runs claude -p --output-format stream-json --verbose with model, effort, --max-turns, --permission-mode acceptEdits, --permission-prompts none, the pre-assigned --session-id and the settings object in --settings: Claude's own sandbox off, the escalation directory among the session's directories, and an allow rule for Bash. Claude's sandbox, when on, runs each Bash command it bounds without a prompt, and a headless worker has nobody to answer one; the rule stands where that auto-allow stood, and the station's sandbox bounds each command. Stream-json under -p needs --verbose; without it the CLI exits 1 and writes no event.

Claude control sessions on CLI 2.1.280

Terminal. A control session needs the zmx pty as its controlling terminal, so the launcher starts it through tycho group-leader rather than tycho session-leader: in its own process group, which the launcher makes the pty's foreground group, with TERM set. The trampoline applies the same session sandbox before it execs the vendor.

Inbox. Each process binds one Unix socket, /tmp/cc-socks/<pid>.sock (under $XDG_RUNTIME_DIR/cc-socks when set, /tmp/cc-socks-<uid> when the shared directory is unusable), mode 0600 in a 0700 directory of the vendor user. The vendor records it beside the session id in <config>/sessions/<pid>.json (messagingSocketPath, status, waitingFor). The registry is writable by the agent user, so a path taken from it is checked against the expected directory, name and owner before the core connects or reads: the socket must be a socket, not a link, named <pid>.sock for the entry's live pid, in one of the vendor's socket directories that is a real directory of the agent user, and owned by the agent user, and after connecting the listener's peer uid must be the agent user's before any byte is written; the transcript must be a regular file of the agent user under the configuration's projects directory, opened without following a link. A resumed session runs under a new pid and so a new socket, which is why the adapter finds the socket by session id in that registry on every call and keeps the path only as the last one observed.

Payload. Newline-delimited JSON: an optional first line {"type":"auth","token":"…"} carrying CLAUDE_CODE_MESSAGING_TOKEN, which only the session's own children receive, then {"type":"user","message":{"role":"user","content":"<text>"}}. The vendor writes nothing back and closes the connection for a delivered line and a malformed one alike, so a post is confirmed only by observation: the registry status turns busy and the transcript records the turn with origin.kind peer. The model sees the text inside a preamble saying it came from another session and cannot grant permissions. Limits: one complete line within 30 seconds of connecting, 1,048,576 characters per message, 100 held messages. An instruction is one ShortText, a reference and never content.

Permission prompts. A session in manual mode stops at a prompt (status waiting, waitingFor permission prompt) and inbound messages queue behind it until someone answers. crossSessionInbound: accept decides only whether a message is delivered, held or refused; it approves nothing, and the vendor tells the model that a peer message is never approval. A control session therefore runs in dontAsk, where a tool use that would prompt is decided by its permission rules instead; under dontAsk the same write instruction left the session busy and then idle, never waiting, and the file appeared.

Settings on resume. --settings applies to the process that receives it: a session started with crossSessionInbound: hold held a message, and the same session resumed without --settings delivered one. The launcher passes the one settings object (Claude's own sandbox off, inbound accept, the auto-compact window) on every start and every resume. A resume needs the transcript the first turn writes: a session killed before its first turn answers --resume with no conversation found and exits, so a control session that dies that early is spawned fresh under a new id.

Relay. The socket admits only the vendor user, so the core, running as the developer, cannot post into an agent user's session. When the socket or the registry refuses the core, the adapter writes the instruction line, wrapped with the target session name and the idempotency key, as a file named by the key's digest into instructions/<session>/ under the agent directory: created by the core, sticky and group-writable (1770), each file 0640 and at most 4 KiB. The session's launcher, running as the agent user, polls that directory once a second (up to eight files a poll), checks that the directory belongs to the core and is closed to other writers and that each file, checked on the descriptor it opened without following a link, is a regular file of the core with mode 0640 or stricter and exactly one link, refuses a file that names another session, is not named for its own key, or whose key already has a posted marker, posts each line to its vendor's socket, and records the outcome in a marker file beside it, <name>.posted or <name>.failed with the decoded delivery; the sticky bit lets it add markers but never replace the core's files. A file already present under the key counts as relayed only when it passes the same checks and holds the same line. Markers do not count toward the 256 unposted instructions a directory may hold. When the session is killed or reaped, the core unlinks the directory's entries and the directory and never opens or writes them, since a planted hard link may share its inode with any file of the core; a link of an instruction left in another session's directory names this session, and that session's launcher refuses it. The inbox socket admits every process of the agent user, so a core instruction and a peer's message look the same at the socket: the instruction is a reference, authority lives in the secret-checked handler that resolves it, and the relay's session, ownership and link checks are a layer in front of that handler, not the boundary. An instruction is never typed into the terminal: one that can neither be posted nor relayed is recorded as refused on the session's view. zmx send, with the carriage return zmx does not add, is for nudges only.

Delivery once. A post is one journaled step with a single attempt, and once any byte of the line is written (a failure mid-write or at the half-close included) it counts as delivered and nothing else sends it. A crash between the write and the journal's acknowledgement replays the step and posts the line again; a relayed instruction is not repeated, because the file for its key already exists and holds the same line.

Vendor sandboxes. Claude gets {"sandbox":{"enabled":false}} in --settings on every start and resume, and Codex runs with --sandbox danger-full-access: the station's sandbox around the whole tree is the only layer (the session sandbox, section 7). A vendor sandbox nested inside it cannot start: with Claude's sandbox on, 2.1.280 answers every Bash call with Sandbox is required but failed to initialize: EPERM: operation not permitted, listen '/tmp/srt-mux-<pid>-<n>.sock', and with its unsandboxed retry allowed the model reruns the command outside it. The launcher's --settings wins over a worktree's .claude/settings.json: with the worktree file turning Claude's sandbox on, the worker's Bash call ran as it does with no worktree setting, while the same object passed by the launcher refused it, which is the observable that tells the two layers apart. Measured in the worker mode by mise run vendor-sandbox-tests; the control mode's settings layer is not probed. Telemetry, error reporting, update checks and the official marketplace's auto-install are off through the vendor's environment (DISABLE_TELEMETRY, DISABLE_ERROR_REPORTING, DISABLE_AUTOUPDATER, CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC, CLAUDE_CODE_DISABLE_OFFICIAL_MARKETPLACE_AUTOINSTALL); a host the vendor still tries off its allowlist is refused at the proxy and recorded.

Trust dialog. The workspace trust dialog appears before the inbox binds and blocks the session; it does not appear when the working directory or an ancestor is trusted in the vendor user's .claude.json, which is part of the agent user's core-owned configuration (section 7).

Compaction and login. The settings object sets autoCompactWindow to 1,000,000, which the vendor caps at the model's window, so compaction can fire only at the vendor's default fraction of the full window. That fraction is not documented and CLAUDE_AUTOCOMPACT_PCT_OVERRIDE can only lower it, so a compaction in a transcript is still detected and reported as a defect. A session authenticates with the token the launcher puts in CLAUDE_CODE_OAUTH_TOKEN (vendor credentials, section 7). The launcher also passes USER and LOGNAME from the password database, under which the vendor looks for a keychain login; the agent user, with no login session, has none it can read, and a separate CLAUDE_CONFIG_DIR or HOME carries no login.

7Durable execution and protocol

The orchestration is a set of Restate services written in Rust. Restate journals every step a handler takes, replays the journal after a crash, runs at most one exclusive handler per keyed object at a time, and keeps timers and promises durable. That covers everything the factory would otherwise hand-roll: queues with leases, retries with backoff, heartbeats, stall timers, signals for verdicts, and restart from a checkpoint. The agent sessions stay outside the engine on purpose: a run that lasts an hour is never a journaled step. The step is the spawn; completion arrives through an awaitable the launcher resolves.

Handlers that change authority (reserve, settle, CaseLaw record, Ledger record, rule) are not reachable from ingress by an agent. Everything an agent legitimately calls (heartbeat, result, escalate) is scoped to its own session key. The Restate admin port is bound to a socket only the core and the reader can reach. The design hands that role to the reader in slice two. The WorkUnit workflow is keyed by the unit id and WorkerRun by the task id, neither with the epic id, a known gap to be closed by prefixing keys with the epic id.

Message payloads

The schemas below are the handler inputs and promise payloads. The envelope fields that the earlier draft carried for delivery (attempt, acknowledgement, idempotency key) are now Restate's: ingress calls from launchers carry an idempotency key of session name plus sequence, deduplicated for a day by default, and the journal gives each step its causation. How an agent run crosses the boundary

  1. A workflow step spawns the session under zmx. The zmx name is derived from the workflow key and attempt. The step first checks the session's lease file: a fresh lease means adopt, a stale or missing one means spawn. It never trusts the zmx list alone, because zmx run on an existing name types into that session instead of failing.
  2. The step creates an awaitable and writes its id, the session's own secret, the session name, the vendor settings and the session's sandbox grants into a spec file readable by the core and the agent group (mode 0640), removed by the core once the lease appears. The typed line carries the launcher invocation with only the spec path and the tier as arguments, bounded at 1000 bytes, because a pty in canonical mode keeps just the first 1024 bytes of what is typed and a secret there would land in the scrollback. For a Claude or Codex session the step also binds the vendor credential's hand-off socket and names it in the spec; the credential itself is in neither the spec nor the typed line (vendor credentials).
  3. The launcher's exit trap writes the result JSON to a spool file first, then resolves the awaitable, retrying until Restate acknowledges, so a core outage at exit time loses nothing. On failure it rejects with the decoded failure state. Launcher hooks call the session's exclusive heartbeat handler with the progress marker, each call carrying an idempotency key. The trap ends by killing its own zmx session.
  4. The workflow races the awaitable against durable timers. T1 on silence sends a nudge through the session object. T2 on an unchanged progress marker saves scrollback, kills the session and re-queues with the attempt incremented. Activity alone never resets T2. Promise and awaitable names carry phase and attempt, because a workflow key runs once and a unit can go through several results, escalations and retries.
  5. If the launcher is killed before its trap runs, nothing resolves; the timer and the reconciler catch it, and the lease decides between adopt and re-queue.
  6. The lease and the spool are enough to choose between adopt and re-queue and to carry a result across a Restate outage; they do not stop the vendor of a launcher killed before its trap, which leads its own session. The reap of a lost session therefore also signals the vendor group recorded in its spool directory, with the same checks as a kill by pid.

Interactive control sessions receive instructions over the vendor's per-session socket, called from a handler step. Text injection into the terminal is for nudges only. Status updates write object state rather than resolving promises, so an hours-long run does not grow the journal by one entry per heartbeat; the run handler reads state when a timer fires.

Context budget and rollover

A control session's context degrades long before the window is full, and the vendor's auto-compaction is a model summarizing its own transcript: unverifiable, and known to drop the brief. The factory does not compact. A control session is disposable, the state is in Restate, and a fresh session starts from a rendered brief; that is the crash path, and it is also the normal path.

  • Small by construction. A control session never receives raw worker output, transcripts or file contents. Workers return a short structured result plus references; status arrives as state; the control session reads the semantic graph and the store, not the repository. A hook caps tool output size.
  • Measured. The Session object carries the session's current context size, reported from the vendor's per-turn usage by the launcher's hooks. The WorkUnit run handler checks it at every heartbeat.
  • Rolled over, not compacted. At a threshold around sixty percent of the window, and at every phase boundary (plan done, dispatch done, verify done) regardless of size, the handler requests a handoff note, kills the session, and spawns a fresh one with the brief rebuilt from state. The rollover threshold sits below the vendor's default auto-compaction fraction of the window; a PreCompact hook in the control session detects a compaction that fires anyway and records it as a defect, an fyi inbox item.
  • The handoff note is structured, not a summary: the objective as now understood, decisions taken with reasons, workers in flight with their awaitable ids, dead ends not to retry, open questions, the next action. It is written through a handler as the session's last act, schema-validated and size-capped, and linted like a packet. The new session's brief is the rendered WorkUnit and Session state, the cases in force, the task packet, and that note.
  • Workers do not roll over. A worker at its threshold is killed like a stall and its task returns as too large; the control session re-plans it into smaller tasks.

The harness measures rollovers per unit and whether a session after rollover repeats a dead end listed in the note, which is the direct test of whether the note carries what matters.

Work unit lifecycle

Routing and fan-out

  • Each task class maps to a minimum tier and an effort; a second table maps tiers to models per vendor. A task packet without a rationale, or with a tier below the minimum, is rejected by the launcher. A retry after failure moves up to the fallback tier.
  • Slot counters per level on the epic object, starting at two control sessions and two workers each, plus a cap on concurrent sessions per seat account. One serialized build-and-verify lane per work unit. Each unit has a cost and wall-clock budget that hard-stops it; the budget is settled on every exit, including cancel and T2 kill, at the larger of the reservation and the observed usage, and each vendor account carries its own spend limit as the outer wall.
  • Two ledgers: seat capacity and metered dollars. Metered vendors are a routing target with their own ceiling, not an overflow that happens by accident when a seat runs dry.
  • Retry backoff starts at ten seconds doubling to a five-minute cap, set as the step's retry policy, which covers the spawn only; agent retries are workflow logic with a per-class attempt cap. First stall timer at five minutes of silence. All numbers are placeholders until the harness sets them.
  • Prompts, routing tables and hook definitions are content-hashed files that a journaled step reads at the start of a unit, so a unit keeps the versions it started with and a prompt edit does not require a new deployment. Service code changes still deploy as a new Restate version, with the old endpoint kept running under zmx until its invocations drain. The routing tables and thresholds are authored in CUE under config/ and exported to config/export, each file beside its SHA-256. The runtime reads them from TYCHO_CONFIG_DIR or <core home>/config, a directory only the core's user can write, or else from the export embedded in the binary; a work unit and each worker run journal the values they start with and use those for the whole run.

Merge gate

The gate is local git plus file ownership, so it works the same for a project on GitHub, GitLab, a bare repo on a server, or no remote at all. Per project the core keeps a canonical bare repository under its own user. Each work unit's worktree is a clone of it owned by the agent user. Children write only to their worktree; they have no write path to the canonical repo, its hooks, or its default branch.

  1. The child's result declares the unit done with the branch name and head SHA in its worktree. The verify step, which is handler code and not an agent, fetches that branch from the worktree path into the canonical repo, checks the SHA out fresh into an empty environment under the core's user, and runs the done criteria and any case checks from copies pinned by content hash in the factory store, never from scripts in the child's branch.
  2. On pass, the same step fast-forwards the default branch of the canonical repo to the verified SHA (or creates the merge commit itself when the unit is behind), records the merge in the journal, and resets the worktree's view of default. On fail, the findings go back to the unit with the attempt incremented.
  3. If the project has a remote, a separate sync step pushes the canonical default branch to it by name with a credential issued to the station's own identity, which only the core holds. On GitHub that identity is a sync App of its own, separate from the release App: the core holds its private key, the App is installed on each project repository it syncs, and each sync mints an installation token scoped to that one repository and to contents write (plus workflows write for a repository whose units change workflow files), revoked after the push. The release App stays installed on the station's own repository with contents and pull requests only, and its key stays in CI. A forge without app identities gets a key bound to that one repository. No credential of the developer's is used. When the project has an entire mirror, that is the remote: faster, off the forge's API limits, and forwarding to the forge of record. Host-side branch protection is optional defense in depth for projects where humans also push; it is never what the factory relies on.

Both steps are journaled, so a crash between the fast-forward and recording it replays to the same answer. Concurrent units are serialized through the canonical repo by the Epic object's merge lane, so two verified units cannot race the default branch. The thin slice proves the gate with three negative tests, run as the agent user once that account is provisioned: a direct write to the canonical repo, an edit to its hooks directory, and a push to its default branch. All three must fail on permissions before any factory code runs. The boundary suite runs them, then the positive path through Repositories: pin fetches the worktree's branch and pins the head, fresh_checkout checks it out detached in the core's staging directory where the criteria run, fast_forward moves the default branch only from an ancestor and names the commit it replaces, and sync pushes that one branch by name, never forced, so pin refs stay in the canonical repository.

Trust boundaries

Three domains. Agents run under a dedicated macOS user that holds no credentials at all: no git host login, no cloud credentials, no SSH keys, no access to the canonical repos, the factory's data directory, the Restate admin port or the reader's secret. The core (Restate, the endpoint, the launcher, the reader) runs as the developer and is the only thing that ever talks to a remote. The human acts only through the reader, which holds the one secret that can resolve a verdict promise. Repository content is untrusted input to every agent, so a prompt injection in a README can at most make a worker produce a bad branch in its own worktree, which verification catches; it cannot touch the default branch, rule on its own packet, refund its budget, or write a binding case.

The user boundary is the security boundary, and inside it the station's own session sandbox bounds every process tree the launcher starts (the session sandbox, below). The vendors' built-in sandboxes are off: they cover shell commands only, not file tools, hooks or MCP servers; they carry a documented unsandboxed retry; they share the agent's uid; and one nested inside the station's cannot start. The launcher passes the vendor settings on every launch, and they win over a worktree's settings (section 6). The agent user's own settings files, shell startup files and the vendor binaries must be owned by the core and read-only to the agent, so that no tool the agent has can widen its own sandbox. A file inside the agent's home cannot meet that: the agent owns the home directory, so it can rename or unlink any entry in it whatever the entry's owner or mode. The settings and startup files therefore belong outside the agent's reach, in core-owned locations the vendors honour (managed Claude settings, ZDOTDIR set from /etc/zshenv, CODEX_HOME in a core-owned directory) or in a root-owned home whose access list lets the agent add entries but not delete them. The property is a gap, listed under clause 7.1 in section 14; xtask setup does not report it. The agent user has its own primary group, tycho-agent, not staff, but that alone does not keep it out of the developer's home: macOS makes every local account a member of staff through the localaccounts group, and a home is commonly staff at mode 0750. A deny entry for the agent in the home's ACL (search, list, readattr, readextattr) does, since the ACL is read before the mode bits; xtask provision-agent adds it as the developer and xtask setup reports the home as open without it. The same entry means every binary the agent runs, the core's own executable and the vendor and zmx binaries included, lives outside the developer's home, in the shared tool prefix /Users/Shared/tycho: the pinned mise and release builds of tycho and xtask in its bin, and a mise data directory holding the pinned claude, codex and zmx. The core's identity, the developer, owns the prefix and every entry beneath it, and none is writable by group or other, so the agent executes and reads but changes nothing; /Users/Shared is sticky, so only the developer or root can rename or remove the prefix itself. A launcher spawner built for the prefix types the prefix's tycho as the launcher and runs the session under the prefix's zmx, both at the absolute paths station.json in the prefix records, with a digest of each tool's install; the session's PATH holds the pinned install directories, never mise's shims, since a shim asks mise which version to run and mise reads version files in the working directory and its parents and cached paths, which the agent can write. Any mise a session starts reads no project configuration, the prefix's read-only cache and no network, and installs nothing. The core's own processes, which run as the developer, keep the developer's tools. xtask provision-agent creates and fills the prefix as the developer, with no root step; xtask setup checks the prefix's owner, mode, ancestors and every entry beneath it, and each tool's path, version and install digest, and, run as the agent, asks the kernel whether the agent can write any entry. The keychain is the reason a separate user is required rather than a sandbox profile alone: it is scoped by user, not by path. The Restate admin port listens on 127.0.0.1, which every local uid can connect to. A session's process tree cannot: its sandbox lets it connect only to its proxy, which refuses loopback. A process of the agent uid that the launcher did not start still can, so the boundary suite's bare agent-uid probe of the port is a measurement, and that remainder is listed under clause 7.1 in section 14. The boundary suite (crates/tycho/tests/boundary.rs, mise run boundary-tests from a terminal) probes each of these boundaries as the agent user and fails on any that answers.

The identity switch. The core starts each launcher session as the agent through one sudoers rule, /etc/sudoers.d/tycho-agent: the developer may run the prefix's zmx, named by its path, as tycho-agent and as no other user, with no password, under umask 007. xtask provision-agent writes the rule to a 0700 directory of the developer's, checks it with visudo -c -f, and has root install it, the one file root writes, in three steps: install -S -o root -g wheel -m 0440 to /etc/tycho-agent.sudoers.tmp, root's own visudo -c -f of that file, then mv -f onto /etc/sudoers.d/tycho-agent. sudo reads every name in sudoers.d without a dot or a trailing ~, and a file there that does not parse makes sudo refuse every command for every user, the developer's own sudo included; install writes its own temporary file, INS@ and six characters, in its target's directory. So the file is installed and checked outside sudoers.d, and only a rename on the same volume puts the complete file there. sudo wraps zmx run, not the launcher: the session daemon zmx forks and the shell it starts are the agent's, the shell executes the typed env -i … tycho launch in place, and the pid zmx list reports is the launcher running as the agent, which the kill path and the credential hand-off key on. With sudo around the launcher inside a developer's session, zmx list reports sudo itself, running as root, and sudo stays the command's parent while it allocates a pty or opens a PAM session, both on by default. The words zmx types into the session do not change, so the switch costs the 1000-byte typed line nothing. The switched run starts from /, since zmx hands its working directory to the session. Every other zmx command in the shared directory (list, kill, history, send, the reader's attach) is the developer's, over a socket the shared group can connect to.

What crosses sudo. Under env_reset sudo sets HOME, SHELL, USER, LOGNAME, MAIL and the SUDO_* variables for the agent, passes PATH (the caller's, or secure_path when the sudoers configuration sets one), and keeps TERM, TZ and the locale variables when its env_check finds them safe. The rule's env_keep = replaces the default kept list, which on macOS holds HOME, MAIL and SSH_AUTH_SOCK, with exactly HOME, ZMX_DIR, ZMX_DIR_MODE and ZMX_LOG_MODE. zmx starts the session's shell as a login bash, which reads /etc/profile and then the startup files in HOME before the typed line runs; the switched run sets HOME to /var/empty, root's and empty, so the listed pid runs no startup file of the agent's before it becomes the launcher. Root's /etc/profile and /etc/bashrc still run. The launcher gets the agent's real home from the typed env -i HOME=…. The agent's startup files for its other shells remain the gap of the startup-files issue.

Reading the rule back. The developer cannot read a 0440 root file, so xtask setup reads the rule through sudo. sudo -n -k -l lists every entry of the developer with its tags, the defaults that match, and the defaults bound to a runas user or a command, one line each when sudo writes to a pipe, as sudo 1.9.17's display_privs prints them; to a terminal sudo wraps lines at its width, and both callers capture through pipes. sudo starts its line count again for the command-bound defaults, so the first Defaults! line is glued onto the last Defaults> line; the decoder splits it. The listing must hold the rule's entry, (tycho-agent) NOPASSWD: <pinned zmx>, and its Defaults!<pinned zmx> line, and nothing else that needs no password: no other NOPASSWD entry, to any user, and no !authenticate default. An entry for another zmx install of the prefix is what a pin bump leaves, and provisioning installs the rule again; any other no-password entry is the operator's to remove. Then sudo -n -k -u tycho-agent -- /usr/bin/true must still ask for a password. A probe of one command with sudo -l <command> shows nothing: the developer is in admin, which may run anything as anyone with a password, and once any entry needs none sudo -l lists without a password and answers "permitted" for anything. The listing's form is taken from sudo's source, not from a capture: no rule existed where it was written. Its decoder reports any line it cannot place as unrecognised, which setup reports as unreachable. Only a session started through the rule shows that zmx itself runs with no password; the boundary suite starts one and requires the listed pid to be the agent's.

The rule restricts less than its text suggests. sudoers names zmx but not its arguments, and zmx run types any command into a shell, so the rule means "the developer's uid may run anything as tycho-agent", which the developer could already do with a password. Its target lives in the developer-owned prefix, so the developer can also replace the binary it names. Neither widens what the developer can do; the rule makes the developer's no-password route to the agent one line to audit, and it is not a restriction on that route. Any process of the developer's uid, not only the operator at a keyboard, has that route. The same uid can swap the candidate rule between the developer's visudo -c -f and root's install; root's check of the installed file keeps a file that does not parse out of sudoers.d, and the listing read after the rename shows what root installed. A zmx pin bump changes the path the rule names, so provision-agent installs it again.

Killing a session. The core runs as the developer and cannot signal a process of the agent's uid. A launcher or vendor that passes every check of the kill path is signalled through the rule instead: a throwaway zmx session, reap.<pid>.<16 random hex digits> so no process of the agent's can hold the name first, started as the agent, whose typed line is exec /bin/kill -KILL -- -<group> for the vendor and … -- <pid> for the launcher; the core waits until that session has ended and the process is gone, and removes the session by name. zmx kill of the launcher's session does not reach the vendor, which leads its own session: zmx sends the launcher SIGHUP and then SIGKILL half a second later, while the launcher gives the vendor's group SIGTERM and five seconds before SIGKILL, so a vendor slower than half a second, and any vendor after a SIGKILL of the launcher, outlives it. In production the kill path reaps it through the rule; only the operator-run boundary test shows that delivery. The launcher, control and chaos suites run the agent as the core's own user, where the kill path refuses to signal, so a vendor outlives its killed launcher there and only the suites' own cleanup ends it; launcher_killed_before_its_trap_resolves_nothing passes through that cleanup. The orphaned vendor issue tracks it.

The shared zmx log. zmx 0.8.1 appends to logs/zmx.log under ZMX_DIR by path, following a link, exits if it cannot open it, truncates it by path past 2 MiB, and reads no variable that moves it. Before every zmx command the core runs in the shared directory, it requires the directory to be its own and sticky (mode 3770), makes logs its own directory at 0750, and keeps zmx.log its own regular file with one link at 0660: a link, a FIFO, another owner's file or a second link at that name is unlinked and the log created again, since the core owns logs and a hard link the agent made elsewhere then keeps only the old inode. The agent can append to the log but can neither rename the directory nor replace the file. The launcher's own zmx command, run as the agent, only checks that the directory is sticky and the log a regular file. The cost: an agent's session daemon cannot create its per-session log in logs, and zmx then logs nothing for that session.

The session sandbox

The station's own sandbox bounds every vendor session, built from the nono library crates (nono and nono-proxy 0.80.0, pinned exactly, without the system keyring), and the vendors' own sandboxes are off (section 6). It is the mechanism for the vendor boundary and for the Restate admin port. There is no nono process: the launcher runs the proxy and the session leader applies the sandbox.

The proxy. Before the vendor starts, the launcher starts a session proxy on 127.0.0.1 at an ephemeral port, serving only that session. It tunnels a CONNECT only to the vendor's allowed hosts, listed per vendor in config/sandbox.cue (Claude: api.anthropic.com; Codex: chatgpt.com, api.openai.com, auth.openai.com), with an empty list refusing everything; it refuses every other host, loopback and the core's ports included; it forwards a request in absolute http:// form only to an allowed host and with its session token, and one in origin form not at all, since the session has no credential route; and it records each decision, up to the 4096 events nono-proxy keeps between drains. The vendor's environment gains the proxy's variables (HTTPS_PROXY and HTTP_PROXY with the token in their user part, NO_PROXY for loopback, NONO_PROXY_TOKEN, NODE_USE_ENV_PROXY), which a headless worker passes on to the CLI, and when the vendor ends the launcher logs the counts and each refused host to its log and stops the proxy. The variables carry the token and are never logged.

The plan. The launcher hands the trampoline, tycho session-leader or group-leader, a plan in TYCHO_SANDBOX_PLAN: the proxy's port, the core's five ports, the session's grants, the vendor's socket directories, the absent paths it may stat and the state files it saves. The core puts the session's own paths in the spec (the prefix's tycho, the session vendor's install and the directory its link points into, a worker's brief and binary to read; its worktree or the control session's working directory to read and write), and the launcher adds its session's files and the vendor's state. The trampoline builds the set from the plan and the station's system-path list, applies it, removes the plan from the environment and execs the vendor. The plan never travels on the typed line, and the launcher builds the set once itself before the vendor starts, so a plan that cannot be built is refused before any vendor process exists.

The set.

  • Network: proxy-only, outbound TCP to the proxy's loopback port and nothing else (Seatbelt (remote tcp "localhost:<port>"); a Landlock connect rule for the port), and on macOS no system resolver: the profile omits the mDNSResponder socket, the proxy resolves the hosts it admits itself, and localhost still resolves from the hosts file. Claude's worker and control sessions run unchanged without it. A set whose port is zero or one of the core's, that reaches the resolver, or that carries another TCP grant or a platform rule beyond its own, is never returned: sandbox::capability_set ends in check_proxy_only, swept over the production ports and the ports of all 1800 test-core slots by no_set_the_station_builds_leaves_proxy_only_or_reaches_a_core_port, and every widening nono offers is refused by the_proxy_only_check_refuses_every_widening.
  • System paths: the read and write groups for macOS and Linux of nono-cli 0.80.0's data/policy.json (that release ships no security-lists.toml), ported into config/sandbox.cue less the entries absent on macOS 26. Every macOS entry must exist when a session starts, and a Linux entry the ci runner may lack is marked optional.
  • The session: read and write on the worktree or working directory, on the session's vendor directory under the spool (the result and progress files, the output schema and the escalation directory), and on the Codex home; nothing else of the spool, so the launcher's lease, log and spool record stay out of the vendor's reach.
  • Claude's state: read and write on ~/.claude and its cache directory, both made 0700 when missing, and on ~/.claude.json with its siblings ~/.claude.json.<suffix>. Claude saves the file by writing a sibling and renaming it over the file, and a grant of the file alone refused the save, so a run under it left the file unwritten (claude_saves_its_configuration_under_the_sandbox, against an unsandboxed run as the positive control).
  • git: read on each configuration file under HOME that exists, and stat of each that does not, which then answers absent instead of the EPERM git treats as fatal for its configuration.
  • Sockets: bind and connect in Claude's inbox socket directory, made 0700 when missing, in the order Claude tries them.
  • Signals to the vendor and the processes sharing its sandbox, so it can signal its own tool children.
  • Nothing on the keychain and nothing else of a home.

Refusals. A grant that cannot be made, an absent or undecodable plan, or a kernel that cannot apply the set is a refusal, never a narrower set or an unsandboxed run: the launcher ends the session vendor_sandbox_refused (inbox) before any vendor process exists, and the trampoline exits 125 with the reason on its standard error and runs nothing, which the launcher decodes, with no result file, as the same vendor_sandbox_refused, so a refusal never returns to the queue to be refused again. On Linux, a Landlock ABI below 4 cannot filter TCP, and nono then asks for a seccomp supervisor the station does not run; that is a refusal, never a pass. The ci runner applies the set on its kernel (crates/tycho/tests/sandbox.rs): from inside, the core's port is refused, the proxy's reached, a granted directory written and a path outside every grant refused.

Processes. The launcher stays the vendor's parent, and the trampoline execs the vendor in place, so the pids the kill path and the credential hand-off key on are unchanged. Measured with ps under the launcher suite: zmx list names the launcher, whose parent is the zmx run daemon and which leads its own group on the session's pty; the vendor's parent is the launcher, its group and session are its own pid, it has no terminal, and its command line is the vendor's own, not the trampoline's; its children share its group.

Residuals.

  • The vendor holds its credential: Claude's token is in its environment and Codex's auth.json in its home, inside the sandbox's reach (vendor credentials). Injecting Claude's token at the proxy, so the vendor holds only a phantom, is the next change; Codex's bearer has no route yet.
  • Setuid binaries, /bin/ps among them, do not run under the sandbox; Claude runs ps at startup and goes on.
  • Keychain lookups are refused: the profile denies the security daemons.
  • The proxy admits an allowed host whatever credential a request carries: a vendor holding another account's key can send it to api.anthropic.com, so the allowlist bounds where traffic goes, not on whose account. The credential route of the next change injects the session's token; it does not stop a request that brings its own key.
  • The proxy keeps 4096 audit events between drains and drops later ones, so a longer session's counts are a lower bound; the launcher's proxy line says when the cap was reached.
  • On Linux the set bounds no DNS (Landlock leaves UDP open), and a pathname Unix socket the file grants reach can be connected: Landlock does not filter connect on pathname sockets, and nono enforces socket grants there only through the file grant.
  • The proxy tunnels a CONNECT that carries no token to an allowed host: nono's lenient mode, which its source gives as the mode Node's clients need, since they send no proxy credentials on CONNECT. A local process outside any sandbox reaches no more through it than it reaches directly, and another session's sandbox reaches only its own proxy.
  • The system-path list is the station's. A macOS or nono update re-runs its existence test (docs/process.md); the read list includes /private, /var, /tmp, /Library, /Applications and /opt, so a world-readable file of another user there is readable.
  • An agent-uid process the launcher did not start is unbounded, so the boundary suite's bare agent-uid probe of the admin port stays a measurement.
  • On Linux, Landlock filters TCP connect by port alone, scopes signals only from ABI 6, and has no pattern rule, so a state file is granted alone and its save is refused; the ci runner runs no vendor.
  • Claude's inbox socket directory is shared: every Claude session of the agent uid binds its socket in one directory, so a sandboxed vendor can connect to another session's inbox, and in the suites, where the agent is the developer, to the developer's own interactive sessions. A per-session directory is the inbox directory issue.
  • In the launcher, control and worker suites the vendor's home is the developer's, so the developer's ~/.claude, ~/.claude.json, git configuration and Claude cache are granted, and the developer's user-level MCP servers are refused at the proxy and recorded.

Vendor credentials

The agent user has no login session, so it has no keychain it can read, and on macOS Claude Code keeps its subscription login in the keychain; Codex keeps its login in a file or the keychain as configured. The core therefore holds one credential per vendor and hands it to each session, and none sits at rest outside a running session's spool directory. Each is the vendor's documented path for a machine without a browser login:

  • Claude: a token from claude setup-token, which the authentication docs describe as a one-year OAuth token for CI and scripts where browser login is unavailable, able to make model requests only, read from CLAUDE_CODE_OAUTH_TOKEN. The pinned CLI's help: "Set up a long-lived authentication token (requires Claude subscription)".
  • Codex: the auth.json that codex login writes under CODEX_HOME (default ~/.codex) when its credential store is file; the authentication docs describe copying it to a headless machine.

Storage. tycho credentials set claude or codex, run as the developer, reads the value from stdin, never an argument, checks its shape and bound (512 bytes for the token, which must start sk-ant-oat; 16 KiB for auth.json, which must hold a refresh token or an API key), and writes it 0600 by a rename into <core home>/credentials, a 0700 directory of the core created one level at a time. tycho credentials status prints each file's presence, owner, mode and age and never its content. xtask setup checks on the developer's side that each file is a 0600 regular file of the developer in a 0700 store, and, as the agent, that stat, listing or opening the store is refused.

Hand-off. The launcher spawner reads the session vendor's credential from the store and refuses to spawn a Claude or Codex session without one. The spawn step binds a Unix socket in the spec directory, which only the core writes, named by a digest of the session name, mode 0660, and writes its path into the spec. Before its lease the launcher connects, requires the listener's uid to be the core's, and sends the session name and secret from the spec. The core answers once, to a peer of the agent's uid whose session name matches and whose secret matches in constant time; it stops after eight refused requests, and closes and removes the socket once the lease appears. A launcher that gets no credential still writes its lease, starts no vendor, and ends vendor_credential_unavailable, which goes to the inbox.

Delivery. Claude gets the token in CLAUDE_CODE_OAUTH_TOKEN, the one credential variable the launcher adds to the vendor's environment, which a headless worker passes on to the CLI. Codex gets CODEX_HOME naming a 0700 directory in the session's private spool directory, holding auth.json at 0600; the launcher zeroes and removes it when the vendor exits, and on a stop before it signals the vendor, since zmx kills the launcher half a second after its hangup. The value is never on the typed line, in the spec, the lease, the spool, the launcher's log or its output.

A socket rather than a file: a per-session file in the instructions directory would be the core's in a sticky directory, which the launcher cannot unlink, so it would stay readable by the agent's group until the core removed it. The socket holds nothing at rest and answers only while the spawn step waits for the lease.

  • The peer-uid check is what keeps other users out. The session secret in the request is defence in depth over it: it travels in the spec, mode 0640, which every process of the agent uid can read, so it does not stop a racer of that uid. Such a process that connects first gets the credential once, and the launcher then ends vendor_credential_unavailable, so the theft is visible, not prevented. The answer is therefore bound to the launcher's pid, the one zmx list reports for the session's running entry, never a pid from the lease, which the agent writes. The server compares it with the peer's pid twice, on connect and again after the request: SO_PEERCRED on Linux records the connector, while LOCAL_PEERPID on macOS reports the last process to use the peer's socket, so the second read names the process that wrote the request. A connection that arrives before the spawn step has read zmx list is held for up to six seconds, within the launcher's ten-second wait for its answer. A racer of the agent uid that read the spec is refused, since its pid is not the launcher's, as long as nothing of the agent's runs in the listed pid before it becomes the launcher; the switched run's empty HOME keeps the agent's startup files out of it (the identity switch, above).
  • The vendor holds the credential for the session's life and the launcher sees it. A process can read the environment of another process of its uid, and the vendor's tools inherit the vendor's environment, so every process of the agent uid can read the Claude token while a Claude session runs, and the Codex home while a Codex session runs. The Claude CLI's subprocess environment scrub forces its permission mode to default and is not used. The credential's reach is the vendor plan.
  • A launcher killed with SIGKILL leaves its Codex home in its spool directory, readable only by the agent uid; the core does not reach into an agent-writable directory to remove it.
  • Codex refreshes its tokens when last_refresh is older than about eight days and writes them back to auth.json, and the vendor's guidance is to keep the refreshed file. The session's copy is removed with its home, so the stored seed never advances: after the window every session refreshes from the same seed, the second session after the vendor rotates the refresh token fails, and two sessions started together race for one refresh token. Those sessions end vendor_login_required until the operator runs codex login and credentials set codex again. Returning the refreshed file to the core is the Codex refresh issue.
  • Removing the Codex home removes Codex's session files with it, so a Codex session cannot be resumed after its launcher ends.
  • Clause 7.4: the Claude token is the narrowest the subscription offers, model requests only, but lasts a year; the Codex refresh token lasts until the vendor rotates or revokes it; and both are issued to the operator's account, not the station's. Neither vendor issues a subscription credential to a service identity or a shorter-lived one to a machine without a login session, and the keychain login they do issue cannot be read by a user without one. The operator rotates both; removing a file stops new sessions, and the Claude token stays valid for its year (docs/process.md).
  • Where the launcher runs as the developer, as the launcher, control and worker suites run it, both ends of the hand-off have the developer's uid and the peer check admits it; the code path is the same.

An escalation, end to end

  1. A worker's launcher rejects its awaitable with a certified question. The WorkerRun workflow returns it; the WorkUnit run handler starts an Escalation workflow and awaits its outcome.
  2. Escalation sorts the question. Empirical: it starts a probe WorkerRun and rules on the result. Authority: it calls Escalation at the parent level. Judgment: it queries CaseLaw; a fresh binding case ends it here.
  3. Otherwise it calls Council, which starts judge runs in parallel as short worker runs with sealed briefs, probes any checkable objection, runs one exchange round, and returns the tally with dissents.
  4. A majority with no standing objection becomes a verdict. Escalation records the case, returns, and the WorkUnit run handler resumes with the case in force.
  5. A split or a boundary crossing calls Escalation at the next level. At the top it starts a DecisionPacket workflow, which writes and lints the packet, publishes it to the inbox, and awaits the verdict promise. The web view's rule action calls the shared handler that resolves it. The packet workflow writes the case and the chain unwinds.
  6. A human stop verdict cancels the WorkUnit invocation; cancellation runs down through the open child invocations and each one's compensation kills its zmx session.

8Escalation and arbitration

Every question is sorted before anything else. A question a script or test can answer is dispatched as a probe and ruled on by the result. A question above the arbiter's authority goes straight up. Only judgment calls reach a council.

Council protocol

  • Required when a change is irreversible, a ruling would bind more than one work unit, precedents conflict or are stale, three sampled rulings by the arbiter disagree, or the arbiter shares a vendor with the author of the work under judgment.
  • Three judges, five for one-way doors. Each judge gets a lens, assigned to vendors at random per case. No council is single-vendor. A council spanning three vendors may rule at binding weight; with the two seat vendors verified in v1, a two-vendor council rules at persuasive weight at most, and any ruling with scope wider than the work unit goes to the human. One-way doors always need three vendors or the human.
  • Each judge starts with a sealed brief: options in random order, the lower level's recommendation hidden.
  • Independent votes first. Any objection that can be checked is tested before anyone argues.
  • One exchange round. A judge may change its vote only by citing a fact it had missed.
  • A ruling needs a majority and no objection left standing. Dissents are kept and travel up the ladder.

The judge literature behind this: majority voting explains most of what debate gains; extra debate rounds can talk models out of correct answers; models within one vendor share mistakes; the minority was right in about one split vote in four, which is why dissents travel.

Case law

One JSON file per case plus a SQLite index, linked into the graph. Retrieval filters by scope, then searches by keyword and embedding. When the fingerprinted files have changed, a binding case drops to persuasive. An arbiter must say, for each retrieved case, whether it applies or how this situation differs. A level is bound by its own level and those above; only a human overrules a human. Human cases carry a short review date and are suspended after two failed citations, so a hurried ruling cannot bind forever. Cases that prove reliable get promoted into hooks or lint rules. Case state lives in Restate; the files and the index are projections, so an agent with filesystem access cannot write a case. Every citation is recorded: when an arbiter applies or distinguishes a case, when a packet lists a precedent, when a mechanism fires naming its article. The citation ledger is what tells a dormant rule from a load-bearing one, and a rule the ledger has never seen is a petition to amend or remove it.

Deep links

Item lifecycle is a projection over the event log: new, claimed, answered, expired, superseded. Claim and answer are appended events, so a TUI and a web view open side by side converge. Restart after a kill

  • Nothing in git is reset.
  • Restate or the service endpoint killed: every handler replays to its last journaled step. Agent sessions under zmx never noticed.
  • A control session or worker killed: its awaitable stays pending until the timer fires; the step that checks the zmx list adopts a live session or re-queues a dead one with the attempt incremented.
  • A re-spawned control session starts from a brief built from the object state. Vendor resume is used only when the worktree path matches and the transcript is small.
  • An escalation points to the checkpoint taken just before it left the unit. The packet names that checkpoint's commit. The ruling becomes a case linked to both, and the unit resumes with the case in force.

How a record reaches the store

  • Handler checks, arbiters, the packet lint and CaseLaw run inside Restate. The handler calls Ledger record as a journaled step beside the decision it records, so a replay writes it once.
  • The launcher runs in the core's domain outside the engine. Its firings (a refused spawn, bare mode detected, an oversized journal entry) travel in the ingress call that resolves the awaitable or sends the heartbeat, under the session name plus sequence idempotency key.
  • Hooks and lints outside Restate (lefthook, the post-edit hook, vendor hooks in agent sessions, the pre-compaction hook) write one JSON record per run into a spool directory, under a temporary name and then renamed. The Reconciler tick drains each spool into Ledger record with the file's digest as idempotency key and deletes a file only after Restate acknowledges it. Records from the agent user's spool are tagged with the agent domain: a session can forge or withhold them, so they are data, and never the only evidence that a core mechanism held.
  • Forge records are read by a core step keyed by suite id and run id, inside the forge's retention; a gap longer than the retention is recorded as a could-not-run firing of the step. Check-run conclusions decode as: success to an examination; failure to a refused firing; timed_out, action_required and stale to could not run; cancelled to could not run, unless a later run on the same ref superseded it, which is not counted; neutral and skipped are not counted and are never examinations. Rule-suite results decode as: pass to an examination; fail to a blocked firing; bypass to a defect firing. Any other value is unrecognised.

Report

  • One row per clause in the map, per case and convention in force, and per mechanism in the map.
  • Columns: citations, firings, examinations, last citation, last firing, citing instruments as kinds with counts, enforcing mechanisms, and state. The states are in force; dormant; unrecorded (the map declares no record source, so under article 15.4 the mechanism's clauses show as gaps); unmeasured (the map declares a record source and the period holds no record from it); and gap (no mechanism, as listed in section 14).
  • Dormant (article 15.3): no citation and no firing within the review period. A dormant rule raises a petition under article 14.4, and the report shows the petition or the case recording why the rule stays. That case carries forward until its fingerprint changes, so the same rule does not raise the same petition every period.
  • The review period, the convention threshold and the petition thresholds are keys in the station's content-hashed CUE configuration, printed with the ledger and with every petition. Article 14.5 holds all of them, the review period of article 15.3 included: set in configuration, reported with every petition, changed only by the operator.
  • Published by tycho ledger as JSON and markdown, as the "Rule citation ledger" row of the metric table (section 17), and in the reader's TUI and web view.

What the ledger check examines

Two parsers read the mandate. xtask check-mandate parses docs/mandate.md in ci and checks the map's completeness. A core step parses the content-hashed copy of the mandate a work unit pinned at its start and checks the records against it. The core check counts three sets: the clauses parsed, the rules and mechanisms in the map, and the records in the review period. It prints each count. It fails when any count is zero, when the map holds fewer clauses than the mandate, when any mechanism is unmeasured, and when the drain or the forge step could not run. An unrecorded mechanism does not fail the check; it is counted, and its clauses stay in the gap list. An empty ledger fails the check.

Fingerprint

A petition's fingerprint is the SHA-256 of the UTF-8 bytes of the JSON object {"counter": …, "key": …, "subject": …} serialized under RFC 8785 (JSON Canonicalization Scheme), with every string normalized to NFC first. The counter is its string form in #PetitionCounter (repeated_ruling, convention_hold, void_finding, dormancy, early). The key is a string:

  • repeated ruling: the question fingerprint and the ruling digest in hexadecimal, joined by a colon;
  • convention hold: the case id;
  • void finding: the article number in decimal;
  • dormancy: the clause id, such as 7.1, or the mechanism id from the map, such as xtask:check-comments;
  • early: the escalation id.

The subject is sha256: followed by the SHA-256 of the bytes below, or null:

  • void finding: the article's heading line as written (such as ## 7. Separation of domains) and the text of each of its clauses in order, joined by a single \n, with no trailing newline;
  • dormancy of a clause, and early: the clause's text;
  • dormancy of a mechanism: the RFC 8785 serialization of the mechanism's object under mechanisms in config/export/mandate.json;
  • convention hold: the RFC 8785 serialization of {"id": …, "scope": …, "holding": …, "fingerprint": …} from the case record, the case's own fingerprint being the one of article 8.1; citations and outcomes are left out, so use does not change the subject;
  • repeated ruling: null, since the key already names the question.

Mandate text is taken from the copy a pass pins at its start: docs/mandate.md at the head of the station's canonical default branch, stored by content hash, with the hash in the pass report and in every packet. A clause's text runs from its number to the end of its paragraph, with each line break replaced by a single space and trailing whitespace removed, so rewrapping a paragraph changes no fingerprint. The counter's value stays outside the fingerprint, so a growing count keeps one fingerprint, and an amended clause or a changed case gets a new one, as a case's own fingerprint does under article 8.1.

New evidence

A decided petition leaves a suppressing case: a rejection case on reject or on a pull request closed without a merge, and an amendment case on merged. Each records the fingerprint and a baseline in the shape #PetitionBaseline gives its counter. The baseline is the counter's value when the case is written: at the verdict for a reject, when the forge reports the pull request closed for a closed one, and at the merge for an amendment case, after the merge's counter resets. A later crossing with the same fingerprint is compared against the latest suppressing case that holds the fingerprint (by recorded time, then case id), and it is new evidence only when it passes that baseline by the counter's minimum increment. A merge also resets the counters the amendment answers, so the pass after a merge raises nothing.

A pass

  1. Pin the thresholds export and the mandate copy, read every counter, and count the keys examined per kind. A pass that examines no key, or cannot read the counters, the export or the mandate, is a could-not-run firing and fails (article 15.4).
  2. Take the counters past their thresholds in a fixed order (void finding, repeated ruling, dormancy, convention hold, then by key) and compute each one's fingerprint.
  3. A petition in state open or amend with the same fingerprint: nothing to do.
  4. A suppressing case, rejection or amendment, with the same fingerprint: without new evidence, the store refuses to raise it, and the pass counts it as suppressed. With new evidence the petition is raised, its supersedes field naming the case, and the packet shows the baseline and the current value.
  5. With open_max petitions in state open or amend, a crossing waits; the pass counts it as waiting, and a later pass raises it once one closes. Nothing is queued: every pass recomputes from the counters.
  6. Otherwise the pass derives the article, takes the article's next sequence number, starts a drafting run, writes the packet in a journaled step, records the petition as open, and records a Ledger citation of the clause with the petition as citing instrument. A sequence past 9,999 (SEQUENCE_MAX) is a defect firing and the petition is not raised.

The article in the packet path is derived per counter. A void finding uses its key. A dormant clause uses its own article, and a dormant mechanism the article of the lowest-numbered clause it enforces in the map; a mechanism enforcing no clause is a map defect the pass reports, not a petition. A repeated ruling uses the lowest-numbered article among the clause ids the question cites, a convention hold the lowest among the clause ids the case cites, and an early petition the clause the ruling names. With no clause to take it from, the article is new.

The drafting run is a worker run of class judge given the counters, the cases and the pinned clause text. It returns the proposed diff, both options' rows, the recommendation with its confidence, and the strongest dissent. Its exit state maps as follows; any state not listed is unrecognised, a defect firing, and the petition is not raised.

A session may ask an arbiter to raise a petition early (article 14.4). Petition packet

A petition is a decision packet in the shape of section 9 and of the blocker packets the WorkUnit run handler writes under the core home's packets directory. It is written at mode 0600, atomically, to <core home>/packets/petitions/<article>-<sequence>.md, with the article derived as above and the sequence counting from 1 per article. The verdict file is <article>-<sequence>.verdict beside it. The inbox item follows section 10: a petition against a human case blocks, which covers a petition whose supersedes names a rejection case and one with a human case among its motivating cases; any other petition is a petition for amendment with no human case, listed in the digest at fyi severity, since no unit waits on it. Silence leaves either open (article 10.3).

  • Header: petition id, fingerprint, counter and key, evidence value and, when raised on new evidence, the baseline and the superseded case; raised at; "Blocks: no unit"; "Default: none".
  • Question: amend the article as proposed, or reject. For dormancy, reject means the rule stays, and the verdict states why.
  • Options: two, amend and reject, each with what it gains, what it accepts, its blast radius (the instruments, cases, conventions and mechanisms that cite the clause, with counts from the ledger) and its reversibility (an amendment is undone by a further amendment; a rejection gives way to new evidence or a changed fingerprint).
  • Recommendation with its confidence, and the strongest dissent.
  • Proposed text as a unified diff against the pinned mandate copy, at most 40 lines; for a dormant rule the diff may remove the clause.
  • Motivating cases with their counts: up to cases_listed_max listed, the total stated.
  • Consequences: the citations, cases and conventions whose standing the amendment changes, and the rows of the article-to-mechanism map it touches.
  • Evidence as ledger records by content reference, the thresholds with their digest, and the mandate copy's hash.
  • The footer counts unverified claims. A packet over the blocker packet's 32 KiB maximum is a defect firing, not a truncated packet.

Verdicts and outcomes

The verdict file has the blocker verdict's form: a first line of amend or reject, an optional second line of rationale up to 280 bytes, at most 512 bytes in all, a regular file owned by the operator's uid, opened without following a link. A reject on a dormancy petition needs the rationale line, since it is the reason the rule stays; without it the verdict is refused and the petition stays open. The verdict watcher reads packets/petitions/ as its own directory before the epic directories, and Epic start refuses the epic id petitions, so the two cannot collide. It rules through the Operator's rule_petition handler, which calls Petitions rule, and renames the file .applied or .rejected so it is read once. Any other content is unrecognised: renamed .rejected with the reason beside it and never applied.

  • amend: Petitions records the ruling as a human case and moves the petition to state amend, and a journaled core step opens the amendment pull request for the operator: a branch petition/<article>-<sequence> from the canonical default branch with the packet's diff applied to docs/mandate.md, titled docs: amend article <article> by petition, with the packet as its body. The station never merges it (article 13.1). Until the forge closes the pull request, the petition counts as open for the fingerprint check and for open_max. On merged, the counters reset as tabled under new evidence, and then CaseLaw record writes the amendment case, scoped to the clause or article, carrying the fingerprint, the baseline and the pull request.
  • reject: CaseLaw record writes a human case scoped to the clause or article, carrying the petition's fingerprint, the baseline, the thresholds digest and the rationale, and the petition moves to state reject. For dormancy the case records why the rule stays (article 15.3); for every other counter it holds that the mandate is silent there by design. The store refuses to raise the same fingerprint again without new evidence, as defined above.
  • No verdict: the petition stays open and counts toward open_max. No timer decides it.

Three zmx 0.8.1 facts shape the shared directory, probed as the developer in a private directory:

  • The process umask masks every mode zmx sets: the socket, which takes no variable, the directories ZMX_DIR_MODE names and the log files ZMX_LOG_MODE names. Under umask 022 the socket is 0755, the log directory 0750 and the log files 0640 whatever the variables say, and the group cannot connect, since connecting needs write permission on the socket. Every zmx run in the shared directory, the agent's sessions and the developer's clients alike, runs under umask 007.
  • Every zmx list and zmx attach opens logs/zmx.log for appending, and an attach the session's own log; either file unwritable to the caller fails the command with AccessDenied. The log files default to 0640, owned by whoever ran zmx first, so both users run zmx with ZMX_LOG_MODE=0660 and ZMX_DIR_MODE=0770. The developer can therefore write the shared log files as well as the sockets; the suite prints each entry's owner, mode, link flag and the developer's write access. Zmx::agent runs every zmx command in the shared directory under umask 007 with both variables.
  • zmx follows a symbolic link at a log path: zmx kill appended its line to the file a link at logs/zmx.log named. A group-writable logs/ would let the agent replace a log file with a link and aim the developer's next zmx append at any file the developer can write. The log directory is therefore the developer's at 0750 in a sticky shared directory (Trust boundaries, section 7); the suite prepares it before its sessions and flags any link it finds there.

Two things a dedicated terminal app would still add: an always-visible sidebar with per-unit colour, and hibernation so dozens of open tabs stay cheap. The reader's TUI covers the first. If the second ever matters, agterm is the candidate: MIT licensed, rendered with libghostty, with a zmx live mode and a control CLI that creates a session with a command, types without stealing focus, exposes status glyphs, and publishes a resumable event stream. Those are exactly the gaps that forking supacode would have had to fill. Supacode stays usable as a viewer, since its panes are zmx sessions too, but nothing in the factory depends on it.

15Open choices

Every choice is now settled. For the record: the durable execution engine is Restate, chosen over Temporal for a single binary with an embedded journal, a first-class Rust SDK, and keyed objects that give one invocation per work unit; the reader and core are Rust; the pane host is Ghostty driven by the reader, with no dedicated terminal app on the critical path; entire.io's parts are adopted as below, after an empirical probe of the CLI and the graph plugin.

Decided: entire.io

Semantic graph in slice zero, pinned to the probed plugin version because its command names changed between the release and the default branch. It runs locally with no network and no login, and its cache sits under the plugin directory, not in the repo. It is per worktree: a cold build on a 1,573-file repository took 42 seconds, warm queries under a second, there is no incremental update, and the cache is keyed on the checkout path, so a shared index on the canonical repo does not fit. The launcher builds it after the worktree clone and rebuilds after each worker commit.

Checkpoints for Claude Code workers in slice one, earlier than first planned, because the probe answered the two questions that held them back. Headless capture works without a login: one print-mode run produced a checkpoint ref linked by a commit trailer. Hooks need not live in tracked paths: they pass through the vendor settings file the launcher already supplies, and entire's git hooks follow the core-owned hooks path. The per-worktree settings file it insists on goes in the worktree's local exclude list. Keeping refs off remotes takes three settings together: the push-sessions option off, a negative refspec on the worktree's push configuration, and hidden refs on every remote the core controls; with those, even a mirror push left them behind. The core keeps transcripts by fetching the checkpoint refs from the worktree into a factory-owned bare repository. Codex and Antigravity are supported but their headless capture is untested; Amp would need an external agent plugin.

Hosted git used as the sync remote, other hosted services deferred. The entire address for this project is a private mirror of the GitHub repository with push-through, not a primary. The sync step pushes the default branch by name to one remote, and when a mirror exists that remote is the mirror: fetches and pushes are faster, the factory's git traffic stays off the forge's API and abuse limits (which the tracker adapter may be using at the same time), and GitHub remains the record because the mirror forwards. Nothing in the factory depends on how quickly that forward completes, since a unit counts as merged when the canonical repository's default branch moves, not when a remote agrees. Checkpoint refs stay local by the worktree's refspec and the canonical repository's hidden refs whichever remote is used. Search needs the hosted side and sees only what is mirrored, so it is not a case-law evidence source for local checkpoints. Resume works from local refs.

Redaction is narrower than the design first assumed: entire redacts what enters git objects (a planted cloud key and a token both came out replaced), while the raw vendor transcript under the agent's home and the metadata file in the worktree stay in plain text. Those live inside the agent user's trust domain and are deleted with the worktree; the core only ever fetches the redacted refs. Requirement R30 is reworded accordingly. Two network behaviours are handled by the launcher: every command checks a public API for a new version once a day with no switch to disable it, which the agent sandbox's allowlist simply refuses; the session-start hook calls the entire service when the origin is a forge URL, which worktrees cloned from the local canonical path never trigger. Telemetry is switched off by environment variable in every agent environment.

Decided: pane host and stack

Pane host: Ghostty plus zmx plus the reader, after a probe of zmx 0.8.1 and Ghostty 1.3.1 showed that zmx covers spawn, nudge, tail, labels and fan-in, and Ghostty's AppleScript dictionary covers tabs, splits, focus by id and typed input. supacode-next is out (Electron, no zmx, overlapping orchestration tools); Swift supacode stays an optional viewer; agterm is the candidate if a sidebar app with hibernation is ever wanted. Stack: Rust throughout (Ratatui, axum, htmx, SSE; launcher, reconciler and CLI in the same crate), for one static binary and one toolchain.

17Slices and evaluation

The pre-mortem sized the first vertical slice at about sixteen components, which is a platform. The build is therefore three slices, each answering questions the research could not, and nothing in a later slice is started until the earlier one passes its tests.

Engineering conventions for the repository

  • Every tool is installed and pinned through mise; nothing is installed by hand or by a workflow step.
  • Logic lives in typed code. Build, check and release tasks are a Rust xtask; there are no bash scripts and no logic in workflow YAML.
  • Continuous integration is one workflow of the repository's own that checks out, sets up mise and runs the xtask; no reusable workflows and no marketplace actions beyond that setup.
  • Git hooks run through lefthook: commit messages are checked by the xtask against the conventional commit grammar, formatting and lints run before commit.
  • Commits are signed; the default branch advances only by squash or rebase merges of pull requests whose titles are conventional commits; history is linear, enforced by the host's ruleset with no bypass.
  • Strictly typed over everything else: CUE before JSON before YAML. Configuration, routing tables, thresholds and the article-to-mechanism map are authored in CUE with CUE as the gate; the runtime reads exported, content-hashed JSON; JSON Schema is generated from CUE, never written by hand; YAML only where a tool forces it, TOML only for mise.
  • Figures are stencil documents: structure authored in CUE, validated by its schema, rendered to SVG and PNG by the xtask, and checked in CI so a figure that drifts fails the build. The design's diagrams use a tycho grammar.
  • Batteries included: the station ships as one binary with its assets, grammars, schemas and themes embedded; nothing is fetched at run time.
